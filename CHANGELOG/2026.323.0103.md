# 2026.323.0103 — fix(comfyui)!: the candy declares the service, the box declares the GPU substrate

## Summary

`candy/comfyui` required `layer-cuda`, and `layer-cuda` requires `layer-nvidia` — the **VM**
GPU contract (driver user-space baked into the image, `nvidia-ctk` present, CUDA runtime
linkable from `/usr/lib64`). A candy's `require:` is composed into **every** consumer, so a
CDI **pod** image inherited that contract too: `comfyui-cdi` (base `podcdi.pod-cdi`, whose own
header says it never composes `layer-nvidia`) re-composed `layer-ffmpeg` + `layer-nvidia` +
`layer-cuda` on top of a base that had already applied and stripped them, and then reported
the VM layer's assertions as failures on a pod that must hold neither:

```
FAIL  check the nvidia-ctk CLI binary lands on the canonical /usr/bin path   [layer-nvidia:4]  exists=false
FAIL  check nvidia-ctk runs and reports a version number                     [layer-nvidia:5]  exit=127
FAIL  check the CUDA runtime library is linkable from the canonical /usr/lib64 path  [layer-cuda:7]  exit=2
```

The checks are correct. The image was wrong: a **candy declares what it needs to RUN; the box
declares the substrate's GPU contract** (DESIGN D-HW-8 — a CUDA workload states its need, and
the grant's mechanism, CDI for a pod and VFIO for a VM, decides what the image carries).

The four files in this diff, and why each one moved:

| File | Change |
|---|---|
| `charly.yml` | `require:` loses `layer-cuda` and keeps `layer-supervisord`, with the reasoning recorded at the field so the next author does not put it back |
| `README.md` | the `Requires` row no longer claims the candy ships CUDA; the usage block shows the two substrate shapes (pod base → `layer-cdi`, VM base → `layer-nvidia` + `layer-cuda`) instead of the long-gone `cachyos.nvidia` box |
| `.agents/skills/comfyui/SKILL.md` | the box stack no longer says the candy pulls `nvidia`/`cuda` in, and the base row names the pod and VM bases |
| `.agents/skills/comfyui-layer/SKILL.md` | `Dependencies` is `supervisord` only, the `(inherited from cuda)` env row is corrected (`CUDA_HOME` belongs to `layer-cuda`), and the usage block shows both shapes |

**Nothing else in the candy needed CUDA.** The plan clones ComfyUI (Python), writes its
start/fetch scripts and supervises `main.py`; it compiles no CUDA translation unit, never
invokes `nvcc` and never links the toolkit. PyTorch arrives from the `cu130` wheel index in
`pixi.toml`, and those wheels **bundle their own CUDA runtime**; the driver comes from the
substrate. So there is no build-time toolkit requirement to keep — not even headers.

**No NVIDIA/VM box in this repo needed the two layers added:** this repo has no `box/`
directory and no `box/*/charly.yml` — the candy lives at the repo root, and every consumer in
the org is a pod box (`comfyui-cdi` in `distro-cachyos` and `distro-fedora`, base
`nvidia-cdi` → `podcdi.pod-cdi` → `layer-cdi`). The VM substrate is its own repo:
`opencharly/vm-nvidia` composes `layer-nvidia:v2026.322.1139` + `layer-cuda:v2026.321.1520` at
its box level, so a VM box that later composes this candy bases on it and inherits the VM
contract where it belongs. The README and both skills now say that out loud, which is the
part a future consumer needs.

## Change classification

A candy's `require:` changes for every consumer, so the subject carries `!`.

**Breaking change + rollback:** yes, breaking for any consumer that took its GPU toolkit from
this candy rather than from its base. In the org today that is nobody — every consumer is a pod
whose base (`nvidia-cdi` → `podcdi.pod-cdi`) supplies `layer-cdi` and, through it, the toolkit,
and the VM substrate `vm-nvidia` supplies `layer-nvidia` + `layer-cuda` itself — but a box that
composes this candy on a bare base (say `cachyos.cachyos`) now gets no CUDA toolkit and no
driver layer, and must name `layer-nvidia` + `layer-cuda` at its own `candy:` level (a VM) or
base on a CDI base (a pod). Rollback is the one-line restoration of
`- '@github.com/opencharly/layer-cuda:v2026.290.1513'` under `require:`, which returns every
consumer to composing the VM contract — including the pod that must not have it.
