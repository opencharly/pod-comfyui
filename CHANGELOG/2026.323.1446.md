## Summary

`comfyui-vram-offload` guards the VRAM behaviour this cutover exists to deliver: the checkpoint reaches the card during a prompt, and the card is given back afterwards. **It has been passing on luck.** This PR repairs the sampler, corrects the prose that explained the wrong mechanism, removes a launch flag that was added on a false premise, and makes a green run record its own numbers.

### 1. The guard sampled slower than the load window it measures

Its loop was `nvidia-smi` (~0.1–0.3 s) + `curl /history` + `sleep 1` — an effective period of **~1.3–1.5 s**. A 24 ms whole-device trace of this pod running real prompts shows the loaded window directly:

| prompt | at or above 4000 MiB | at or above 5000 MiB | peak | rise over pre-prompt |
|---|---|---|---|---|
| 1 | 1.40 s | 0.91 s | 5253 MiB | **+1942 MiB** |
| 2 | 1.97 s | 1.23 s | 5259 MiB | **+1828 MiB** |

The checkpoint **is** fully resident. The old loop held **0–1 samples** inside that window and could miss a 1.22 s prompt entirely, which is what the two recorded red runs reported on a device that had loaded the model correctly:

```text
.check/check-comfyui-pod/2026.323.1247   feature-run-rebuild  FAIL: "peak rose 420 MiB, expected >= 1024"
.check/check-comfyui-pod/2026.323.1308   feature-run          FAIL: "peak rose 4 MiB, expected >= 1024"
```

And it is a race, not a state change: inside run `…1247` the same check passed three times and failed once on one steady device — PASS at prompts of 1.34 s and 1.79 s, FAIL at 1.22 s.

### 2. `--enable-dynamic-vram` is a no-op and is removed — not as the fix

The host journal shows ComfyUI's `Model BaseModel prepared for dynamic VRAM loading. 1639MB Staged.` line **with and without** the flag:

```text
14:05:34  WITH the flag:    that line at 14:05:50 (1.79 s) and 14:06:12 (1.22 s)
14:43:09  WITHOUT the flag: the IDENTICAL line at 14:43:38 (2.82 s) and 14:44:13 (1.90 s)
```

So it changes no loading behaviour on this pod and is one more thing to keep true. **Removing it does not fix the guard** — the sampler fix does. It goes because it earns nothing, and both changes travel together because both were wrong about the same mechanism in `v2026.323.1242`.

### 3. The prose that asserted the falsified mechanism is corrected

`.agents/skills/comfyui/SKILL.md` and the launcher's rationale both stated, as current fact, that the flag *streams* the checkpoint and that the check *samples once per second*. Neither survived measurement, and the skill body is baked into the image label by `charly box generate` — this repo's own `AGENTS.md` says a candy change and its skill change land together, so shipping the sampler alone would have published the false claim.

### 4. The measurement is now RECORDED, not only printed

The check runner keeps a step's stdout **only when the step fails** — a measured PASS is literally `exit=0`. So the observed peak and margin had no home on a green run. The step now appends one row per run to `${BASE}/charly-vram-offload.log`, failures included.
