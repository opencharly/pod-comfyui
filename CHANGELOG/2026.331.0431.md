# 2026.331.0431 — feat(box): the comfyui-cdi image and its bed, and the launch-flags check that rejected a correct launcher

## Summary

Move the `comfyui-cdi` box and its `check-comfyui-pod` bed out of `distro-cachyos` into the repo that
owns the service (`AGENTS.md` "Repo classes and naming": a bed lives with the thing it tests).

**The box** composes the LOCAL `comfyui` candy — the box proves this tree, not a pinned release of
itself; the candy's own `require:` brings `layer-supervisord` at its tag — plus `pod-dbus`, on the CDI
pod base. The project header declares what the distro copy inherited: the `podcdi` and `cachyos`
namespaces imported at the project root, and the pixi/aur builder vocabulary (a builder map does not
cross a namespace boundary).

**Moving the bed exposed a real defect in this repo, fixed here.** The bed's first run failed one step:

```
FAIL  check the emitted launch line carries every flag the recipe promises  [comfyui-launch-flags]  exit=1
  the launch line in /opt/comfyui/start-comfyui.sh must run the pixi env interpreter, not bare python:
  launch line: exec "${COMFY_PY}" /opt/comfyui/main.py --listen 0.0.0.0 --p…
```

The launcher **does** run the pixi interpreter — `COMFY_PY="${HOME}/.pixi/envs/default/bin/python3"`
(charly.yml:687) then `exec "${COMFY_PY}"` (:695) — but the checker demanded the literal
`.pixi/envs/…python` substring **in the exec line**, so it was red on a correct image. It now resolves
the exec's *program* through its assignment in the same file: the literal path passes, an exec of a
variable the launcher assigns a pixi interpreter passes, and **bare `python` is still rejected**. The
bed was red on a correct image, which is the one thing a runtime gate must never be. Filed as
`opencharly/pod-comfyui#58` (blocking, claimed, closed by this PR).

It also adds the canonical `.gitignore` entries the build needs (`.containerignore`,
`.dockerignore`, `.check/`, …); this repo had none.
