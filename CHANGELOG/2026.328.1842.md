# 2026.328.1842 — fix(start): launch ComfyUI under the pixi interpreter, never bare python

## Summary

The start script launched ComfyUI with **bare `python`**, which resolves through PATH to the distro
interpreter. The pixi environment's `bin` is on PATH and ahead of the system dirs, but it ships
`python3` and no bare `python`, so the lookup falls through — and ComfyUI v0.46.1's `main.py:20` is
`from app import governance`, whose line 15 is `import yaml`. PyYAML is installed into the pixi env
(`pixi.toml: pyyaml = "*"`) and nowhere else, so the import failed, exit 1, three spawns, then FATAL.
Outside: a published port that accepts and resets, with no app behind it.

Measured in the live container before the change (opencharly/pod-comfyui#52):

```
$ charly cmd comfyui-cdi 'command -v python; python -V; python -c "import yaml"'
/usr/sbin/python
Python 3.14.10
ModuleNotFoundError: No module named 'yaml'
```

| File | Change |
|---|---|
| `charly.yml` | launch under `${HOME}/.pixi/envs/default/bin/python3`, refuse to start when it is missing (exit 78, named reason), print the interpreter; the launch-line check requires the pixi interpreter and rejects bare `exec python` |

Before the change, the same image on the same host gave `comfyui FATAL  Exited too quickly` and
`ModuleNotFoundError: No module named 'yaml'` on every spawn.

**The check fails without the fix.** The launch-line check now greps the launcher for the pixi
interpreter and rejects `exec python`; with the old launch line it reports
`the launch line in … must run the pixi env interpreter, not bare python` and exits 1. This is the arm
that was missing: the check asserted the line existed and carried the VRAM flags, but never asked
*which* interpreter, which is why the defect survived review.
