# 2026.323.0114 — feat(comfyui): a configurable VRAM headroom for a shared GPU

## Summary

ComfyUI now keeps a configurable amount of VRAM completely free and unused, counting VRAM held by other
applications — a policy knob for a GPU shared with other work.

**Successor to #22.** That PR carried the same scope and went `CONFLICTING`: #25 merged
(`3fd3da145ba9e404b1b8a824da31228bfc890b1c`, tag `v2026.323.0103`) and rewrote this same file — it removed
the candy's `require: layer-cuda` and restructured the reasoning prose — so #22's branch could not
fast-forward. Only the VRAM-headroom half is carried over. The `layer-cuda` pin move #22 also carried is
moot here, because the new file has no `layer-cuda` require at all. #22 is closed as superseded.

Head `605553d6de5354e5960258e90f3d9474ae7a3b38`. Diff, from `git diff --numstat origin/main...HEAD`:

```text
13	1	charly.yml
1 file changed, 13 insertions(+), 1 deletion(-)
```

Every item in that diff, and nothing else:

1. `env:` gains `COMFYUI_VRAM_HEADROOM: "1"`, with the comment #22 already had: it is a POLICY knob for a
   shared GPU, not a memory-saving claim.
2. the launcher's `exec` line gains `--vram-headroom "${COMFYUI_VRAM_HEADROOM}"` on its own continuation
   line, with the comment carrying v0.45.3's own help text.

**The flag is upstream's, quoted from the tag this candy pins** (`COMFYUI_REF: v0.45.3`), not from memory —
v0.45.3's `comfy/cli_args.py`: *"Set the amount of vram in GB for DynamicVRAM to maintain as extra headroom
above default. ComfyUI will try and keep this much VRAM completely free and unused, even counting VRAM
from other apps."* Declared as `COMFYUI_VRAM_HEADROOM`, default `"1"`, overridable per deploy:
`charly config comfyui -e COMFYUI_VRAM_HEADROOM=4`.

**What this is not.** It is not a memory-saving fix and this body makes no such claim. An earlier revision
of #22 also carried `--disable-smart-memory` and `--enable-dynamic-vram`; both were withdrawn after
measurement: with the same 2 GB checkpoint and the same generation, idle VRAM was byte-identical at
**368 MiB** on the patched and unpatched images, and `enables_dynamic_vram()` in the pinned tag returns
true unless a conflicting flag is passed, so `--enable-dynamic-vram` is a no-op here. Both stay out. If a
reviewer believes they belong, say so and I will answer with the measurement rather than adding them
silently.

## Change classification

The candy's `env:` gains one variable with a default and the container's launch line gains one argument.
A deployment that does not set `COMFYUI_VRAM_HEADROOM` launches with `--vram-headroom 1`; one that sets it
launches with that value. Same port, same volume, same service, same build inputs.

**Breaking change + rollback:** none — a consumer that sets nothing keeps working unchanged and simply gets
1 GB of headroom, which is ComfyUI's own policy default rather than a new contract; rolling back is
reverting this branch, after which the server falls back to its own default reserve.
